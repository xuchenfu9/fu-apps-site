# FU apps 内容与性能刷新设计

**日期：** 2026-07-28  
**状态：** 已确认，待实施

## 目标

将五个已发布应用的介绍从三个简短功能标签扩展为五个有证据支持的体验段落，改善产品辨识度；同时统一公开联系邮箱，并降低 GitHub Pages 首次访问时的图片传输量。站点继续是零后端、零追踪的 Astro 静态网站。

## 内容原则

- 首页使用更完整但仍可快速扫读的摘要；应用页以编号的五项“核心体验”说明展开。
- 每项功能均须能在对应应用工程、App Store 上架资料或已审核的公开文档中找到依据。不得把规划、内部实验或未实现行为写成已提供能力。
- 文案以场景、组织方式和用户获得的结果为中心，而不是堆叠技术名词；五种站点语言分别撰写，而不是由浏览器翻译。
- 证件照产品可说明尺寸、底色、人物分离、修图和导出辅助；必须明确最终接受与否取决于使用机构，不保证任何证件或申请获批。
- 所有产品页、法律页面、支持页、页脚和维护文档使用 `fxcpxs@163.com`。该邮箱是所有者此次指定的唯一公开联系地址。

## 资源策略

- 保留现有 `public/assets/apps/<slug>/` 的 PNG/JPEG 作为原始批准素材；不覆盖、不重命名。
- 在同一应用目录下新增 `web/`，保存由原图生成的 WebP 副本。应用数据改为引用 WebP；原图仍可追溯和复用。
- 通过受版本控制的 `npm run optimize:media`（Sharp）生成图标不大于 256px 的 WebP，截图按最大边 1200px 生成高质量 WebP。产品页首张截图使用 eager 加载，其余截图保持 lazy loading。
- 页面继续提供 `width`/`height` 或稳定容器尺寸，避免图片替换导致布局跳动。

## 防回归

- 内容验证要求每个语言版本恰有或至少有五个完整功能段落，并要求每个 `AppRecord` 的公开邮箱为指定邮箱。
- 法律文档测试检查五个语言、三类文档均存在，且所有生成页面使用统一邮箱。
- 新增应用文档要求提供五项已验证功能、WebP 派生素材及原图来源，防止将大图直接作为首次展示资源。
- 交付前运行单元测试、内容验证、类型检查、静态构建与桌面/手机端 Playwright 检查。
