# FU apps 内容与性能刷新实施计划

> **执行说明：** 每个步骤保持单独、可审查的变更；原图不覆盖，所有对外功能陈述须由工程或公开资料支持。

## 1. 先建立约束测试

**文件：** `tests/scripts/check-content.test.ts`、`tests/data/legal.test.ts`、`scripts/check-content.mts`

1. 为公开邮箱常量、每语言至少五项完整功能说明和法律内容中的统一邮箱添加失败断言。
2. 更新内容检查器，在构建前报告违反上述规则的应用和语言。
3. 运行 `npm test`，确认基线在尚未更新数据时因预期约束失败。

## 2. 扩写五语产品数据

**文件：** `src/data/apps.ts`

1. 将五个应用的摘要改为清晰、可扫描的体验描述。
2. 为每个语言版本提供五项功能，依据规格中的可靠功能表；证件照文案保留机构审核免责声明。
3. 将佳佳证件照的 `contactEmail` 改为统一邮箱。
4. 运行内容测试，确认通过新的功能和邮箱规则。

## 3. 统一法律与维护材料

**文件：** `src/data/legal/jiajia-id-photo.ts`、`docs/legal-source-map.md`、`docs/adding-an-app.md`、既有设计说明

1. 将证件照法律资料的邮箱更新为统一邮箱，使三类法律页随工厂生成逻辑自动同步。
2. 更新来源映射，保留原始文档位置并记录发布站点采用的所有者指定邮箱。
3. 更新新增应用清单：要求五项有依据的功能、统一邮箱、原图与 `web/` 派生资源分离。

## 4. 生成并接入 WebP 派生资源

**文件：** `public/assets/apps/*/web/*`、`src/data/apps.ts`

1. 使用 `npm run optimize:media`（Sharp）从每个已批准原图生成 WebP；图标限制在 256px，截图限制在最大边 1200px。
2. 保持原文件不动，在 `web/` 下写入匹配的派生文件。
3. 将应用目录指向 WebP 路径，保留现有响应式稳定尺寸与延迟加载策略。
4. 比较资源总大小并以构建输出确认所有引用存在。

## 5. 验证与发布

**文件：** 构建产物（不提交）

1. 执行 `npm test`、`npm run validate`、`npm run check`、`npm run build`、`npm run test:e2e`。
2. 在本地查看首页与五个产品页的桌面/手机视口，检查更长的功能清单、语言切换和法律页面邮箱。
3. 提交经过验证的源码、文档和派生 WebP，推送 `main` 触发 GitHub Pages 部署。
